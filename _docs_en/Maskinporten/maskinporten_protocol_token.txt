About
Using JWT Grants Towards The Endpoint Is Documented In RFC 7523, Section 2.1.
The 'Aud' Field of the Jwt Must Be Set Equal to the Issuer Identifier of the Machine Gate and Must Only Contain A Single Value. Using the token-endpoint url AS Audience is no Longer valid.
Request
The Client Requests a Token by Passing a Jwt Grant to The /Token Endpoint.
| Header parameters | Value |
| --- | --- |
| Http method | Post |
| Content-Type | Application/X-WWW-Form-Urlencoded |
The Following Request Body Attributes Shall Be Used When Pass the JWT-Grant:
| Attribute | Value | Description |
| --- | --- | --- |
| Grant_Type |   | Type of Grant The Client is Sending, IE.   |
| Assertion | String | The JWT Grant |
There is no need to perform client authentication when using this grant, as the client is implicitly authenticated by the Certificate in the JWT.
See JWT Grant for Requirements for Constructing the JWT Grant.
Example Request:
`` `
Post /Token http /1.1
Host: Test.makerport.no
Content-Type: Application/X-WWW-Form-URENCODED
assertion =
& Grant_Type = URN%3Aietf%3Aparams%3aoAuth%3Agrant-type%3ajwt-Bearer
`` `
Response
The response is a set of tokens and associated metadata, and Will Denden upon what was requested.
| Claim | Description |
| - |- |
| access_token | An oauth2 access token, Einher by Reference or as a JWT Depending on which scopes was required and/or client registration properties. |
| Expires_in | Number of Seconds Until this access_token is no Longer valid |
| Scope | The List of Scopes Issued in the Access Token. Included for the Convenience for the Client, and Should Not Be Trusted for Access Control Decisions.  |
Please note that the access token is opaque for the client, and the format may be changed. Thus the client should not inspect/validate the token contents.

The Access Token
Machine gate issues only self-contained tokens:
| Token Type | Description |
|-|-|
| By Value | The token is self-contained, meaning it contains all the relevant information about the authorization (client, organization, scope, hourly stamp etc.).  Such tokens Are non-reefocable and should have a short lifetime |

Access Token Validation
The Client and Resource Server Must Validate All Responses from the Machine Gate According to the OAuth2 Standards as Well as Best Practice Recommendations from the IETF.
Access tokens must always be validated by the resource server / API Before Granting Access. Some Key Steps in the Validation Are:
* verify that the issuer of the token is machine gate ()
* verify that the token is signed
* Verify that the signature is created by the signing keys of the machinery published at our /jwks-endpoint
  * You should cache the signing Keys of the machine gate for Say 24 Hours and avoid calling the /jwks-endpoint for EACH Token Validation.
* Verify that the token Contains The Expected OAuth2 Scope
Clients Should Normally Just Pass the Access Token Along to the Resource Server Without Any Processing of It, However IF Any Processing Is Performed, Clients Must Also Perform Such Validation.

* RFC6819: OAUTH2 Threat Model
* Draft RFC: OAuth 2.0 Security Best Current Practice
