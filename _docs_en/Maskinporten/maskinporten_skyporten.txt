What is the cloud port?
The cloud port allows you to use the machine gate to share access to sheltering resources.

There is a method that puts together

The machine gate as identity provider
Identity Federation shelf products at the cloud suppliers
Access control patterns to specify access to resources in the cloud

The short version is that you are free to share what you want from your cloud to an organization number with minimal configuration.
You can therefore use the machine gate and the collaborative portal as today to access the board of shotguns such as. an bigquery table, an S3 file bucket, or a current.

The cloud port is especially useful for sharing sheltering resources out of or between cloud suppliers.
Can I use it?
Yes. The cloud port as a concept is tested by the Norwegian Digitalisation Agency and cross -sectoral data collaboration in the transport sector and together with selected providers and consumers. It is not yet covered by SLA or, and the pilot must be evaluated for continuation.  All contact and use increase the chance of this being continued, so contact us.

Access to the cloud port for providers
The cloud port uses the machine gate, and you must therefore first get started with the machine gate as API provider.
See also the guides below for setups related to each cloud supplier.
Access to the cloud port for consumers
The cloud port uses the machine gate, so to get something divided via the cloud port, you also need an integration (OAuth2-Client). 
A good alternative is to use simplified onboarding for machine gate with keys. 
More detailed documentation can be found here.

What cloud supplier do I have as a provider?
GCP
Everything OK! Access with differentiated on org number and/or scope is supported. See guide here.
Azure
Everything OK! Access with orgnr and scopes is supported by the cloud gating on the scope at the end of the sub-field in the token. See guide here.
Aws
Everything OK! Access with orgnr and scopes is supported by the cloud gating on the scope at the end of the sub-field in the token. See guide for consumer and provider here.
Second
If you have a supplier that supports the WorkLoad Identity Federation, it may be enough for you to also share through the cloud port. Feel free to contact us to get started.
Architecture
Central aspects of architecture:

Provides access to sheltering resources based on Consumer's organization number
Using national joint component (machine gate) for authorized access
The security and infrastructure are completely operated by DIGDIR and cloud supplier
Enables effective sharing of large analytical data sets
The cloud supplier is used OIDC-based ID-Federing
Consumer is not given an email or user in your supplier's ski account
Standard-based (OIDC/OAUTH2)
No keys or other secrets must be shared from the data provider's sky account
