Introduction
"Machine Gate" is an OAuth2 Authorization Server (ISSUs) that offers a simple model for API protection based on so-called "2-legged OAuth", see Server-TO server OAUTH2, inspired by Google's System accounts.
On this page, we document how API providers provide the opportunity to self-service their own API protection.
Read the integration guide for API providers first.  API consumers should look at the Integrsation Guide for API consumers and self-service API for integrations

Description of APIs
In the Machine Gate context, an API is the same as an OAuth2 scope. Norwegian Digitalisation Agency wants to give API providers great freedom to decide for their own semantics for API protection within the framework of the OAuth2 standards. At the same time, there is a need for some rules to ensure interoperability.

Visibility
The attribute is used to set the scop's visibility:
| Value | Description |
|-|-|
| Public | The scop is visible to everyone on /scopes /all endpoints.    |
| Private | The scop is not visible to anyone other than API provider and the consumers that have accessed | Consumer must be told that the scop is available |
| Interal | Intense Use in Norwegian Digitalisation Agency |   
Note that there is no integration with the API catalog, so the API provider itself must ensure that the scop does not end up in the API catalog if used.
Scope restrictions
The attribute places guidance on the use of a scope. One or more types of integration may be allowed. If this attribute is set, one of the values must include the "machine gate" in order for you to use the scop with a machine gate client.
Whitelisting of access
API provider can choose to disable the access control of an API/Scope.  There may be several reasons to use this:
- API provider wants to perform the access control locally as part of the API instead of the machine gate
- Apiet is "open" ie everyone should be able to retrieve data, but you want to track who uses it
To activate this feature, the attribute is set on the current API scop.
Inactive entities
To ensure legal logging and statistics, the Directorate of Digitization will never delete scopes and infections (or integrations), but rather disable them at Delete-call.
Disabled entities will not come up in Get listings as default, but can be retrieved by setting as a query parameter. Disabled entities will not be reactivated by mail and you get 409 Conflict instead.

3. Consumer makes an integration
The consumer must register an integration (= OAuth2 client) to use the access in question. The consumer can either make a new client, or update an existing one.  In general, we recommend creating a new safety grounds, since clients should not get for wide access (ie too many scopes).  This is done at the ID port's API for self-service of integrations.
